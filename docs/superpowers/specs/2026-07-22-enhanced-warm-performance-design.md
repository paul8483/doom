# Enhanced Warm Performance — дизайн

**Дата:** 2026-07-22
**Статус:** in progress — Task 3 done (session store; same-map reload 0 compute)
**Контекст:** Enhanced Texture Quality (ветка `texquality`, Tasks 1–9)
дал видимое улучшение картинки, но замер Task 9 зафиксировал цену:
первый прогрев Enhanced — **~85 секунд** (E1M1 и E1M7), и её платит
**каждая Enhanced-загрузка карты**, включая переходы между уровнями
(кэш вариантов живёт вместе с картой). Интерактивный вердикт: для старой
игры на современном железе (8C/16T + SSD) минуты ожидания неприемлемы.

## Причина, а не симптом

85 секунд — это не стоимость hot-switch и не стоимость рендера. Это
CPU-конвейер подготовки данных (дедизеринг → Super-xBR ×2 ×2 → controlled
mips → height → нормали → sharpen для спрайтов/UI) на ~500 элементов,
выполняемый **однопоточно, по одному элементу на кадр**. Отказ от
runtime-переключения Classic/Enhanced («как в современных играх —
рестарт») не убрал бы ни секунды: считалось бы то же самое при каждом
старте. Поэтому режимы и hot-switch **сохраняются как есть**, а чинится
сама подготовка — тремя ступенями.

## Цель

1. **Параллельный прогрев:** все трансформы — чистый C# без
   Unity-зависимостей; выполнять их на worker-потоках (`Parallel`/Task
   pool), главный поток только загружает готовые буферы на GPU.
   Гейт: первая Enhanced-загрузка **≤ 15 с** на 8-ядернике (ожидаемо
   8–12 с).
2. **Сессионный кэш:** обработанные CPU-результаты переживают
   перезагрузку сцены; набор текстур эпизода почти общий → переходы
   между уровнями не пересчитывают ничего (только быстрый re-upload).
   Гейт: повторная Enhanced-загрузка/переход — **0 построенных**
   элементов, время сопоставимо с Classic-загрузкой + upload.
3. **Дисковый кэш** по идентичности WAD + версии пайплайна: результаты
   сохраняются в `persistentDataPath`; холодный старт игры читает с SSD
   вместо пересчёта. Гейт: старт с прогретым диском **≤ ~5 с** до конца
   warm-фазы. Побочная ценность: готовая инфраструктура кэша для
   будущего нейроапскейл-эксперимента.

Инварианты:

- Пайплайн обработки (алгоритмы, константы, порядок стадий) **не
  меняется** — только то, где и когда он выполняется. Golden-снапшоты
  остаются действительными.
- Детерминизм: параллельный результат побайтно равен последовательному.
- Classic не затрагивается; hot-switch и все инварианты texquality
  (ownership, fallback, exact Classic restore) сохраняются.
- Content rule не нарушается: дисковый кэш — производная WAD, создаётся
  в runtime у пользователя (`persistentDataPath`), в билд ничего не
  печётся.
- GPU compute не используется (портируемость CPU-пути обязательна).

## Архитектура

### Ступень 1: параллельный прогрев

Ключевая проблема текущего кода: прогрев зашит в кэши
(`TextureCache`/`SpriteCache`/`HudTextureCache`), которые не
потокобезопасны, и продублирован в двух местах (`MapLoader` load-фазы и
`GraphicsModeController.WarmEnhancedAssets`). Дизайн:

- **Разделение job/integrate.** Каждый кэш получает пару методов:
  `TryCreateJob(id) → EnhancedJob?` (главный поток: снимает immutable
  вход — native `DecodedImage`, wrap, флаги слоёв, категорию; `null`,
  если вариант уже есть/failed) и `Integrate(id, EnhancedJobResult)`
  (главный поток: кладёт результат в словари, создаёт `Texture2D`,
  учитывает байты). Словари кэшей трогает **только** главный поток.
- **`EnhancedJobRunner` (pure `Doom.Graphics`).** Выполняет
  `EnhancedJob → EnhancedJobResult` (albedo mips / normal+height RGBA /
  sprite RGBA / HUD RGBA) — чистая функция, без Unity API. Именно она
  крутится в `Parallel.ForEach` c
  `MaxDegreeOfParallelism = ProcessorCount - 1`.
- **`EnhancedWarmScheduler` (`Doom.MapBuild`).** Единственный
  оркестратор прогрева, используемый и load-фазами `MapLoader`, и
  hot-switch'ем `GraphicsModeController` (дублирующиеся циклы warm
  удаляются). Главный поток: собирает work-list → отдаёт worker-пулу →
  каждый кадр забирает готовые результаты из
  `ConcurrentQueue` и интегрирует с **бюджетом времени на кадр**
  (~6–8 мс аплоадов), обновляет прогресс плашки.
- **Отмена:** `CancellationToken` при `ClearContext`/смене сцены;
  результаты, пришедшие после отмены, отбрасываются без интеграции.
- **Ошибки:** исключение в job'е → результат-ошибка → `Integrate`
  помечает failed state и native fallback (существующая семантика,
  теперь per-item через очередь).
- **Ленивый путь** (дроп/снаряд, впервые запрошенный в геймплее)
  остаётся синхронным одиночным — как сейчас.

Потокобезопасность трансформов: `DeditherFilter`, `AlphaBleedGuard`,
`SuperXbrUpscaler`, `SharpenFilter`, `HeightMapGenerator`,
`NormalMapGenerator`, `PaletteMipGenerator` — статические чистые функции
без разделяемого состояния; аудит фиксируется тестом детерминизма
(N текстур: parallel == sequential побайтно).

### Ступень 2: сессионный кэш

- **`EnhancedVariantStore`** — process-lifetime синглтон
  (`ConcurrentDictionary`), живёт вне сцены. Ключ:
  `(wadIdentity, itemKind, itemId, layerConfig, pipelineVersion)`;
  значение — CPU-результат (`EnhancedJobResult`).
  - `wadIdentity` — существующее понятие идентичности WAD из Stage 7d
    (save preflight); несоответствие → store очищается.
  - `layerConfig` — флаги слоёв профиля, участвовавшие в построении
    (закрывает известную дырку «кэш по имени, а состав слоёв из
    профиля» для послойных captures).
  - `pipelineVersion` — константа `EnhancedPipelineVersion.Value`;
    **любое** изменение трансформов обязано её инкрементировать
    (правило в комментарии константы; golden-тесты страхуют).
- Порядок разрешения при прогреве: **store → (диск, ступень 3) →
  compute**. Хит store = только re-upload на GPU (быстро); промах →
  job в worker-пул, результат публикуется в store после интеграции.
- GPU-объекты по-прежнему per-map (ownership-модель texquality не
  меняется) — переживают сцену только CPU-буферы.
- **Бюджет памяти:** CPU-копия ≈ GPU-объёму (~370 МБ) и удерживается
  всю сессию; managed heap вырастет до ~1 ГБ суммарно. Для desktop
  приемлемо; фиксируется замером. Опции сжатия store — вне объёма,
  записать как ограничение.

### Ступень 3: дисковый кэш

- **`EnhancedDiskCache`**: один pack-файл
  `persistentDataPath/EnhancedCache/<wadHash>-v<pipelineVersion>.bin`
  (заголовок: magic, версия формата, wadHash, pipelineVersion; далее
  индекс + блобы записей). Никаких тысяч мелких файлов.
- `wadHash` — SHA-256 файла WAD, считается один раз на старте
  (~0.1–0.2 с для 28 МБ), кэшируется на сессию.
- **Запись:** инкрементально в фоне по мере готовности job'ов (или
  одним проходом после первого полного прогрева); temp-файл + atomic
  rename; ошибка записи не фатальна (лог + работа без диска).
- **Чтение:** на старте warm-фазы фоновым потоком; повреждение/
  несовпадение хэша/версии → файл игнорируется и перезаписывается.
  Никогда не роняет игру.
- Хранение сырое (без сжатия) в первой версии: SSD читает ~500 МБ за
  1–2 с; простота и устойчивость важнее места. Deflate — опция потом.
- Тесты и editor-запуски по умолчанию направляют кэш во временную
  директорию/отключают запись (детерминизм и чистота CI).

### Поток данных прогрева (итоговый)

```text
work-list (главный поток)
   │  per item
   ▼
EnhancedVariantStore hit? ──да──► re-upload (бюджет на кадр)
   │ нет
   ▼
EnhancedDiskCache hit? ──да──► store.Publish → re-upload
   │ нет
   ▼
worker pool: EnhancedJobRunner (чистый CPU)
   │ ConcurrentQueue
   ▼
главный поток: Integrate (Texture2D, счётчики)
   → store.Publish → disk.Write (фон)
```

## Сознательно не входит

- Изменение самих алгоритмов обработки (порт Super-xBR, веса, порядок
  стадий) и любые визуальные изменения.
- Удаление runtime-переключения Classic/Enhanced и «рестарт при смене
  режима» — не решает причину и ломает существующие инварианты.
- Сжатие store/диска, GPU compute, стриминг мипов.
- Кэширование Classic native (и так быстрые).
- UI-настройки кэша; максимум — очистка каталога при несовпадении
  версии.

## Тестирование

### EditMode

- Детерминизм: для фиксированного набора Freedoom текстур/спрайтов
  parallel-прогон `EnhancedJobRunner` побайтно равен последовательному.
- `EnhancedVariantStore`: publish/lookup, инвалидация по wadIdentity /
  layerConfig / pipelineVersion.
- Кодек pack-файла: roundtrip записи/чтения; повреждённый файл (обрез,
  битый magic, чужой хэш) → чистый промах без исключений наружу.

### PlayMode

- Первая Enhanced-загрузка: warm завершается, counts/bytes равны
  последовательной версии; прогресс монотонен.
- Отмена: смена сцены посреди warm → нет исключений, нет утечек,
  повторная загрузка корректна.
- Переход между уровнями: второй уровень строит **0** элементов
  (всё из store), варианты корректны.
- Диск: холодный запуск с существующим pack-файлом строит 0 элементов;
  несовпадение pipelineVersion → полный пересчёт и перезапись.
- Hot-switch, lifetime, E1 smoke — регрессия существующих сьютов.

### Замеры (в baseline notes)

На 8C/16T: первая Enhanced-загрузка (цель ≤ 15 с), переход между
уровнями (цель ≈ Classic + upload), холодный старт с диска (цель ≤ 5 с),
повторный switch (не хуже 11–19 мс), пик managed/native памяти.

## Критерий готовности

1. Первая Enhanced-загрузка на 8-ядернике ≤ 15 с; переход между
   уровнями без пересчёта; старт с дисковым кэшем ≤ ~5 с.
2. Параллельный результат детерминирован (побайтные тесты зелёные).
3. Hot-switch/ownership/fallback инварианты texquality не нарушены;
   полные сьюты + Windows build зелёные.
4. Замеры до/после записаны в baseline notes; texquality Task 10
   (sign-off) проводится уже с новым прогревом.
